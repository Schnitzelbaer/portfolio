## Context

swissgeol has an archive for geological documents of national importance. The documents inside cover topics such as borehole profiles, geological maps, seismic measurements, lab analyses and reports.

Each document or document group covers a geographic area and is displayed on a web-based map application called “assets”.

For now, the application is designed for the data curators who maintain the federal archive. Read access is open to the public, but only a small selection of documents is available so far. In the long term, the archive should also serve engineers, planners and researchers looking for information about the Swiss subsurface.

## Problem

The archive holds more than 13'000 files, many of them decades old. Nobody had ever recorded in detail what information they contained, let alone where in a file it sat. Some documents run to several hundred pages. Even with the right file open, you could end up scrolling through it page by page, hunting for the one section that mattered for your question. And a single geometry often had several documents attached, all with cryptic technical names. Which one held what? You couldn’t tell without opening each of them. Describing 13'000 files by hand was out of the question, and with more sources feeding in their archives, the problem would only get bigger.

## Task

Make the content describable without curators going through every file by hand, and make it visible to them at a glance.

## Approach

The user base is small: around ten data curators, two of whom were directly involved in the design process. Instead of doing classic user research, I worked in close co-creation with these two experts and the development team and tested drafts with them continuously.

## Solution: extraction and classification for data curators

I redesigned the classification process for data curators around an AI-assisted extraction. For each file, the AI records format, size, page count, language and the content types it contains, with their page ranges.

Newly uploaded files are extracted automatically. The extracted content can then be corrected.

[Screen: Screencast, split view: a document is uploaded on the left, its card appears on the right, is analysed and shows the extracted table of contents; page numbers are corrected in the edit view]

<Decision title="Collapsed by default">
  The first version of the classification view was overloaded when tables of contents were long. Now the items are collapsed by default: you see right away which files exist, and you expand only what you want to edit.
</Decision>

## Solution: asset preview and PDF viewer

The previous detail view listed the asset’s information without a clear structure, and files only appeared with their file names. Based on the extracted data, each file now shows its content at a glance. An expandable table of contents lists the content types with page ranges and languages.

[Screen: File card before and after, side by side and labelled]

<Decision title="Documents before metadata">
  Originally, the asset’s metadata came first. The experts wanted to see the documents first. Metadata is read in a second step and matters mostly for filtering and search. So the documents come first.
</Decision>

Clicking an entry in the table of contents opens the PDF viewer.

[Screen: Screencast: an entry in the table of contents opens the PDF viewer, its tabs are clicked through, and closing the document returns to the start]

<Decision title="Group the table of contents by type, not by page">
  At first, the detected content blocks were sorted by page number, in the order they appear in the document. My analysis revealed a different use case: you have a place in mind and want to know which borehole profiles exist there. So the blocks are now grouped by content type.
</Decision>

## Reflection

<Outcome type="achieved">
  Classification and the detail view are live. Data curators can now describe the content of the archive: newly uploaded files are processed automatically, existing ones on demand. In the detail view, you see what a file contains before opening it, and you can jump straight to the relevant pages.
</Outcome>

<Outcome type="expected">
  We are still working on an enhanced search, so that files can also be found by their content in the future. As more cantons feed in their archives and access opens up step by step, the structured data will make historical information about the Swiss subsurface more accessible to authorities, planners and researchers, for example for construction projects, infrastructure planning and research.
</Outcome>

<Reflection title="">
  - **A small user base needs a different method.** With around ten data curators as the user group, I worked in co-creation with two involved experts instead of doing classic research. The decisions rest on two perspectives. A broader validation is still open.
  - **No baseline.** Because the content had not been described before, there was no existing process to compare against. So I measure success by what the product makes possible, not by time saved: [Add the criterion].
  - **Open issue: trust in the AI.** There are currently no confidence indicators, and after a correction you cannot tell that it happened. One option would be to show where the AI was uncertain and what a person changed.
</Reflection>
